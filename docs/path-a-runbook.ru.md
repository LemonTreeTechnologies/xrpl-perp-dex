# Церемония миграции Path A — рунбук оператора (RU)

**Статус:** production-grade. Церемония выполнялась на реальном SGX-железе (Azure DCsv3) на кластере из 3 нод многократно — bundled HW E2E (2026-05-15), populated-state re-run (2026-05-18) и seal-policy cutover REQ-17 (2026-05-22). Рунбук отражает то, что эти прогоны показали. Спецификация: `docs/audit/REQ-7.md` (приватный репозиторий).

---

## 1. Что такое Path A

Координированное кластером обновление perp-dex энклейва на новый MRENCLAVE **без потери клиентского состояния** (XRPL-ключи операторов, FROST-доли, perp-позиции, балансы вольтов, account pool). Каждый оператор запускает церемонию локально на своей машине; cross-operator SSH нет.

**Path A даёт:**
- Средства в escrow остаются доступны — XRPL-ключи подписи переживают bump MRENCLAVE через церемонию миграции.
- Клиентское perp-состояние сохраняется — клиенты не видят сброса балансов или открытых сделок.
- Кворум операторов решает, можно ли проводить апгрейд (delegation bundle).

**Path A НЕ покрывает:**
- Первичный bootstrap (`node-deploy` без `--side-by-side`).
- Disaster recovery, если OLD-энклейв умер до завершения своей церемонии.
- Cross-host миграцию — Path A привязан к тому же физическому SGX-CPU.
- Cross-posture миграцию — проверка LA-репорта отклоняет debug-пира, когда импортирующий энклейв не debug (A-PA-1 hardening, REQ-18). debug→non-debug миграция отклоняется by design: переход debug→production — это **fresh bootstrap** (`node-deploy` без `--side-by-side`), а НЕ Path A-миграция — экспортированное состояние debug-энклейва недоверенно. Path A применим только внутри одной posture (debug→debug на testnet, non-debug→non-debug в production).

**Когда запускать:** любой bump MRENCLAVE, который должен сохранить живое состояние — security-релиз, re-key seal-политики (REQ-17), любое изменение enclave-кода, разворачиваемое на кластер, уже держащий клиентское состояние.

## 2. Предусловия

1. **Воспроизводимая сборка, MRENCLAVE согласован.** Каждый оператор независимо собирает NEW-энклейв из согласованного git-ref через GHA-пайплайн и подтверждает, что MRENCLAVE бит-в-бит совпадает у всех операторов (INV-BUILD-1). Сборка также прогоняет seal-policy gate (`check-seal-policy.sh`) — сборку, не прошедшую gate, разворачивать нельзя. **Git-ref ОБЯЗАН быть на уровне REQ-16 + REQ-17 или новее** — более старые сборки несут известные дефекты миграции (недоразмерные host-буферы; ре-верификация манифеста на каждой загрузке). См. §7.

2. **Кворум операторов согласовал** NEW MRENCLAVE вне канала (звонок / подписанное сообщение) ДО того, как кто-либо пред-устанавливает NEW-юнит. Церемония затем собирает **delegation quorum** подписей — этот кворум равен кворуму XRPL SignerListSet escrow'а (**2-of-3** на текущем кластере из 3 нод). Каждый оператор, готовящий церемонию, должен знать, сколько со-подписантов ожидать. Delegation bundle доказывает согласие криптографически; пред-согласование — это дисциплина оператора.

3. **OLD-энклейв запущен и здоров** на порту 9088, sealed-состояние в `/home/<user>/perp/accounts/`. Проверка: `systemctl is-active perp-dex-enclave` → `active`.

4. **Артефакты сборки разложены** у каждого оператора: `enclave.signed.so`, `perp-dex-server`, `build-manifest.txt` с зафиксированным ожидаемым MRENCLAVE.

5. **Одноразовая настройка NEW-стороны машины** (только первая церемония на данной машине): установить `perp-dex-enclave-next.service`, `systemctl daemon-reload`, создать `/home/<user>/perp-next/`, пред-разложить `perp-next/config.json` (порт 9089). Постоянная — переиспользуется каждый следующий цикл.

## 3. Церемония — ПАРАЛЛЕЛЬНО по всем нодам

> **Инвариант §11.10 — церемония ОБЯЗАНА идти параллельно на каждой ноде. НЕ мигрируйте одну ноду до конца перед стартом следующей.**
>
> Почему: шаг delegation-quorum церемонии требует, чтобы кворум операторов подписал одобрение, а оператор подписывает через маршрут `/pool/sign` своего энклейва — который **retired**-OLD отклоняет (RETIRED-гейт). Если закончить node-1 первой, OLD node-1 уходит в retired и больше не может со-подписывать; как только N-1 OLD'ов ушли в retired, церемония последней ноды не может набрать delegation quorum. Каждый OLD должен оставаться живым, пока каждая нода не прошла свою фазу export+delegation. Запускайте все ноды вместе. Восстановление после нарушения — в §7.1, но профилактика — единственная протестированная гарантия.

**3.1 — Side-by-side деплой (каждая нода, можно последовательно — недеструктивно).**
Каждый оператор на своей ноде:
```
perp-dex-orchestrator node-deploy --side-by-side --enclave-dist ./dist-new
```
Устанавливает NEW-артефакты в `perp-next/` и стартует NEW-энклейв на порту 9089 рядом с OLD (9088). NEW поднимается с пустым sealed-состоянием + эфемерной migration-keypair, сгенерированной внутри SGX. Проверка на каждой ноде: `curl -k https://localhost:9089/version` → NEW MRENCLAVE.

**3.2 — Запустить церемонию на ВСЕХ нодах одновременно.**

**Пользоваться пусковым скриптом. Не набирать три curl'а руками.**

```
bash orchestrator/scripts/ceremony-parallel.sh preflight   # только готовность, ничего не запускает
bash orchestrator/scripts/ceremony-parallel.sh dryrun      # репетиция на трёх, обратимо
bash orchestrator/scripts/ceremony-parallel.sh real         # НАСТОЯЩАЯ
```

Почему скрипт, а не три curl'а ниже. §11.10 — единственный инвариант, у которого нет
проверенного восстановления, и требуемая им профилактика была записана как «каждый оператор на
своей ноде, в одно и то же время». Это предполагает трёх операторов. Когда все три узла держит
один оператор через один бастион, ручной запуск И ЕСТЬ последовательное нарушение — три curl'а
одновременно набрать нельзя, а §7.1 при потере этого окна заканчивается пере-бутстрапом
оператора по пути, который на железе никогда не проверялся.

Арифметика при кворуме 2 из 3: если node-1 снимет свой OLD, пока node-3 ещё собирает делегации,
у node-3 останется ровно два подписанта — на грани; если раньше уйдут два, останется один, и
узел застрял. Параллельность не убирает это окно — она делает так, что ранние фазы
перекрываются и каждый узел собирает делегации задолго до того, как любой дойдёт до последнего
шага.

Вторая половина — ПРЕДПУСКОВАЯ ПРОВЕРКА, и она отказывается запускать что-либо, пока не готовы
все три узла: OLD обслуживает с ожидаемым измерением, NEW отвечает ровно целевым,
`perp-next/accounts` ПУСТ, все три службы активны, оркестратор несёт исправление шага 5a, и в
allowlist ровно одна запись **с одинаковым дайджестом на всех трёх** — потому что «одна запись»
на каждом узле ничего не говорит о том, одна ли это и та же. Узел, который не готов, падает
ПОЗДНО, когда остальные уже сняли свои OLD, а это ровно та ситуация, для которой существует
§7.1. Каждый из этих отказов пробит мутацией, а не предположен.

Режим `real` излагает последствия обычными словами и требует набрать фразу — это не флаг `-y`.

Ручной эквивалент, для справки:
Каждый оператор на своей ноде, в одно время:
```
curl -sS -X POST http://127.0.0.1:7095/admin/migrate-state \
  -H 'Content-Type: application/json' \
  -d '{"expected_mrenclave_new":"<hex 64>"}'
```
(`--migrate-admin-listen 127.0.0.1:7095` должен быть задан оркестратору; гейтится через `--signers-config`.)

На каждой ноде драйвер: запрашивает у NEW target_info + свежий ceremony nonce → просит NEW сгенерировать эфемерную keypair → собирает delegation quorum (§2.2) через libp2p signing-relay → просит OLD проверить LA-репорт NEW + delegation + зашифровать состояние → просит NEW проверить LA-репорт OLD, расшифровать, M3 durability self-check, записать M4-манифест ПОСЛЕДНИМ → просит OLD проверить completion-репорт и запечатать свой retired-marker.

Каждая нода возвращает `200 OK {"status":"ok", "ceremony_nonce_hex":…, "mrenclave_new_hex":…, "manifest_hash_hex":…}`. Разные ceremony nonce на нодах — ожидаемо.

> **Точка невозврата:** запечатывание OLD-энклейвом своего retired-marker — последний шаг церемонии. **До** неё abort безопасен (OLD продолжает обслуживать, NEW отбрасывается). **После** неё OLD в retired, а NEW перезапечатал состояние под новым MRENCLAVE — откат на OLD-энклейв невозможен (§4.6).

## 4. Пост-миграционная верификация

Выполнить на каждой ноде до promotion. Не делать promotion на частичном результате.

1. **NEW MRENCLAVE** — `curl -k https://localhost:9089/version` → ожидаемый NEW MRENCLAVE, все ноды.
2. **First-boot autoload** — перезапустить NEW один раз; `enclave.log` показывает `migration manifest verified — post-migration boot`, `sealed SignerList loaded`, `Auto-loaded ... account(s)`, `Auto-loaded perp state (chunked)`. Migration-манифест **поглощается** при этой первой верификации (переписывается `file_count=0`), чтобы последующие загрузки после операционных изменений состояния не спотыкались о file-hash проверку.
3. **Выживание состояния** — пробить известный баланс пользователя и вольт: `curl -k --get --data-urlencode "user_id=<r…>" https://localhost:9089/v1/perp/balance` и `…/v1/perp/vault/status?type=1`. Сравнить с до-миграционными значениями.
4. **Полнота sealed-файлов + политика** — каждый sealed-файл в `accounts/` NEW должен присутствовать (ожидаемый per-shard набор) и быть MRENCLAVE-policy. `key_policy` — это uint16 LE на байт-офсете 2 каждого `sgx_sealed_data_t` — `0x0001` = MRENCLAVE, `0x0002` = MRSIGNER. Проверять каждый файл, не выборку.
5. **OLD retired** — OLD возвращает `PATH_A_ERR_ECALL_RETIRED` (-150) для signing/state-mutating ecall'ов; `path_a_retired.sealed` присутствует в `accounts/` OLD; read-only маршруты (`/version`) ещё отвечают.
6. **Необратимость** — OLD-энклейв (другой MRENCLAVE) больше не может расшифровать перезапечатанные файлы NEW. Это намеренное конечное состояние: откат на pre-NEW энклейв невозможен, как только NEW перезапечатал. Подтвердить, что это понято как осознанный operational checkpoint.

**Если любая проверка §4 провалилась — см. §7.2. Не делать promotion, не делать decommission OLD.**

## 5. Promotion

Продвинуть NEW в канонический слот `:9088`, чтобы оркестратор (нацеленный на `--enclave-url …:9088`) драйвил NEW. На каждой ноде:

1. `sudo systemctl stop perp-dex-enclave-next perp-dex-enclave`.
2. Установить NEW в `perp/`: заменить `perp/enclave.signed.so` + `perp/perp-dex-server` на NEW-сборку. **Отодвинуть sealed-состояние OLD — не перезаписывать его:** `mv perp/accounts perp/accounts.OLD-<old-mrenclave>`. Затем установить состояние NEW: `cp -r perp-next/accounts perp/accounts`. Сохранённая `accounts.OLD-<old-mrenclave>` — forensic-копия до decommission §6.
3. Очистить `perp-next/accounts/` (пусто) — готово к следующему циклу миграции.
4. `sudo systemctl start perp-dex-enclave` → `:9088` теперь поднимает NEW. `perp-dex-enclave-next` оставить остановленным.
5. Проверить `:9088/version` = NEW MRENCLAVE; autoload-цепочка зелёная; оркестратор переподключился.

### 5.3 Заново провести управление allowlist — ОБЯЗАТЕЛЬНО после промоушена

**Path-A не переносит `trusted_mrenclaves.sealed`.** Найдено 05.10.2026 инвентарной разницей
сухого прогона, одинаково на всех трёх узлах: у OLD 183 запломбированных файла, миграция
записывает 182, и остаётся именно управляемый allowlist. В `kPathASectionTable` для него нет
записи — причём у `recent_nonces.sealed` есть явное решение «INTENTIONALLY NOT migrated» с
написанным обоснованием, а у этого файла нет ничего, то есть это упущение, а не выбор. Это же
объясняет наблюдение §11.4: на кластере с 14 завершёнными миграциями allowlist отсутствовал
вовсе.

**На промоушене ничего не ломается.** SELF доверен всегда неявно — «кластер не должен иметь
возможности запереть себя, даже с пустым или откатанным allowlist» — поэтому продвинутый NEW
обслуживает нормально, а узел, входящий с ТЕМ ЖЕ измерением, допускается без allowlist.

**Теряется раунд управления**, и единственный его потребитель — СЛЕДУЮЩИЙ подъём MRENCLAVE,
чей экспорт будет отказывать с `-25`, пока allowlist не внесён заново. Поэтому после
промоушена повторить:

```
bash orchestrator/scripts/govern-b18-and-dryrun.sh      # с MRENCLAVE = НОВОЕ измерение
```

Сделать это сразу, а не на следующем подъёме, иначе следующий подъём начнётся с видимости
поломки по причине, к нему не относящейся. Сухой прогон сообщает об этом в поле `followups`
на каждом запуске — чтобы это отдавалось оператору, а не держалось в памяти.

**Правильное исправление на будущее** — запись в таблице секций, по образцу `pinned_unl.sealed`
(optional=true, добавлен ровно по этой причине: «управляемый UNL обязан переживать смену
MRENCLAVE»). Это правка анклава, поэтому ей место в следующем подъёме, а не в этом.

## 6. Decommission OLD — ОБЯЗАТЕЛЕН

Decommission OLD-энклейва **не опционален и не «оставить бэкап на пару недель».** `accounts.OLD-…` — это устаревшая копия клиентского состояния; бинарь энклейва для MRENCLAVE OLD воспроизводим из исходников, поэтому sealed-состояние OLD не является криптографически гарантированно инертным. Устаревшие копии sealed-состояния — это остаток и поверхность экспозиции — прямой урок инцидента seal-политики MRSIGNER (INCIDENT-2026-05-20).

На каждой ноде, **после того как верификация §4 пройдена и promotion верифицирован**:
1. Процесс OLD уже остановлен (§5.1). Отключить OLD-юнит, если он был отдельно определён.
2. **Затереть** sealed-состояние OLD: удалить директорию `perp/accounts.OLD-<old-mrenclave>`, сохранённую в §5.2, плюс любые архивные/snapshot-директории прошлых циклов. Аудит-запись держать в `docs/` + памяти, не как sealed-блобы на диске.
3. Если миграция вывела из эксплуатации on-chain escrow в рамках изменения — проверить on-chain баланс старого escrow перед затиранием его ключевого материала: подтвердить, что ничего ценного не застревает.
4. Re-scan: подтвердить, что осталась только `accounts/` активного энклейва, все sealed-файлы ожидаемой политики, ноль устаревших директорий.

Не примешивать sealed-состояние других приложений в эту зачистку — только perp-dex директории.

### 6.1 §6 не очищает `perp-next/`, и СЛЕДУЮЩЕЕ разворачивание из-за этого отказывает

Найдено 04.10.2026 при подготовке β18; иначе всплыло бы посреди церемонии.

`node-deploy --side-by-side` отказывает, если в `perp-next/` есть что-либо кроме предоставленной
личности узла (`config.json`, `perp.pem`). После прошлого цикла на всех трёх узлах оставалось:

    accounts/              (ПУСТ — ноль файлов, проверено)
    enclave.signed.so      устаревший, сборка не та, что разворачивается
    perp-dex-orchestrator  устаревший
    perp-dex-server        устаревший
    civetweb_access.log, enclave.log

То есть **разворачивание откажет на каждом узле, пока `perp-next/` не очищен**, а в §6 об очистке
не сказано ничего. Отказ приходит на первом же шаге следующей миграции — под тем самым дефицитом
времени, который у церемонии есть всегда.

**Очищать безопасно, и это проверено, а не предположено.** `perp/` и `perp/accounts` — настоящие
каталоги, а не ссылки в `perp-next/`, поэтому живое состояние от него не зависит; а
`perp-next/accounts` **пуст**, значит запломбированного состояния там терять нечего. Удаляются
пустой каталог, два лога и три устаревших бинарника.

**Добавить в §6, после вывода старого из строя:** очистить `perp-next/` до `config.json` и
`perp.pem` — эти два суть одноразовая подготовка машины из §2.5 и должны остаться. Перед удалением
убедиться, что `perp-next/accounts` пуст; если он **не** пуст — остановиться и выяснить почему, это
означало бы, что продвинутый набор оставили на месте, а не перенесли.

## 7. Режимы отказа и восстановление

| Симптом | Причина | Восстановление |
|---|---|---|
| `node-deploy --side-by-side` отклоняет "OLD service not active" | OLD-энклейв остановлен/нездоров | Перезапустить OLD; разобраться, почему остановился |
| отклоняет "NEW unit not found" | Пропущена одноразовая настройка (§2.5) | Установить systemd-юнит |
| отклоняет "perp-next/ not empty" | Недоделанная прошлая попытка | Очистить `perp-next/accounts/`, повторить |
| отклоняет "MRENCLAVE mismatch" | Артефакты сборки ≠ build-manifest | Выяснить, какой энклейв запущен, до повтора; никогда не продолжать на mismatch |
| церемония возвращает `ERR_DELEGATION_QUORUM` | Слишком мало операторов подписали; ИЛИ нода была мигрирована до конца первой и её OLD ушёл в retired (нарушение §3) | Собрать недостающие подписи; если OLD ушёл в retired рано → §7.1 |
| церемония возвращает `ERR_NONCE_REPLAY` | Повторно использован тот же nonce | Свежий nonce генерируется на каждый вызов; если срабатывает на действительно свежем nonce — подозревать RNG: снять `recent_nonces.sealed` обеих нод и связаться с dev-perp |
| церемония таймаутит на confirmation | NEW не смог запечатать мигрированный файл | OLD НЕ ушёл в retired (confirmation не получен — abort ещё безопасен, §3 точка невозврата). Изучить `enclave.log` NEW; перезапустить NEW + повторить со свежим nonce |
| пост-миграционный рестарт: энклейв отказывается стартовать, `PATH_A_ERR_FILE_HASH_MISMATCH` (-17) | До-фиксовые сборки ре-верифицировали migration-манифест каждую загрузку; операционное изменение состояния затем ломало file-hash проверку | Текущие сборки (≥ REQ-16) **поглощают** манифест после первой успешной верификации — это не происходит. Если видно на текущей сборке — write-back манифеста не удался: изучить `enclave.log`; манифест можно удалить вручную (энклейв тогда трактует состояние как pre-migration) |
| export падает `PATH_A_ERR_BUFFER_TOO_SMALL` (-2) | До-REQ-16 host-буфер мал для заполненного состояния | Исправлено в текущих сборках (4 MB export-буфер, 16 MB transport-буфер). Пересобрать с ref ≥ REQ-16 |
| частичная миграция кластера — часть нод на NEW, часть на OLD | Церемония ноды упала посередине | Кластер транзиентно терпит split. Перезапустить церемонию на упавшей ноде **пока остальные OLD ещё живы** (не делать promotion/decommission, пока все ноды не на NEW) |

### 7.1 Застрявшая нода — нода не может набрать delegation quorum (нарушен §3)

Нода «застряла», если её церемония падает с `ERR_DELEGATION_QUORUM`, потому что N-1 OLD'ов уже ушли в retired. Retired OLD'ы не могут со-подписать — `/pool/sign` под RETIRED-гейтом.

**Восстановление (best-effort, не протестировано в проде):**
1. **Promoted** NEW-энклейв не в retired и держит мигрированный pool-ключ оператора — он *может* обслужить `/pool/sign` delegation-запрос. Поэтому: полностью **сделать promotion** каждой уже-мигрированной ноды (§5), чтобы её оркестратор драйвил NEW на `:9088`.
2. Перезапустить церемонию застрявшей ноды. Её сбор delegation теперь достигает promoted NEW-энклейвов через libp2p relay; их подписи верифицируются против SignerList (идентичности операторов не меняются при миграции).
3. Если кворум всё равно недостижим — у застрявшей ноды **нет in-place восстановления**: её надо пере-bootstrap'нуть как свежего оператора (полный bootstrap — SignerListSet + DKG; см. процедуру bootstrap), затем заново присоединить.

Этот путь восстановления **не отрабатывался на железе**. Единственная протестированная гарантия — параллельная дисциплина §3 — трактовать §3 как **обязательное, не рекомендательное**. Профилактика и есть восстановление.

### 7.2 Верификация §4 провалилась после того, как церемония вернула 200 OK

К моменту §4 церемония завершена: OLD в retired, NEW перезапечатал состояние (точка невозврата §3 пройдена — откат невозможен). Если проверка §4 падает (выживание состояния, полнота, политика):

1. **Стоп.** Не делать promotion (§5). Не запускать decommission OLD §6 — `accounts/` OLD (всё ещё в `perp/accounts/` на этот момент, ещё не отодвинута) — единственная оставшаяся копия до-миграционного состояния и forensic-доказательство.
2. Оставить оба энклейва как есть. OLD в retired (не подписывает), но его sealed-состояние цело и читаемо энклейвом с MRENCLAVE OLD.
3. Эскалировать dev-perp с: упавшей проверкой §4, `enclave.log` NEW, `manifest_hash_hex` церемонии, листингами `accounts/` обеих нод. Восстановление отсюда case-specific и не является рутинной операторской процедурой.

## 8. Recent ceremony nonces — заметка о crash-окне (LR-IMPL-3)

`recent_nonces.sealed` OLD обновляется ПОСЛЕ успешного encrypt + продукции LA-репорта, но ДО `verify_import_confirmation`. Есть микросекундное crash-окно между encrypt-success и nonce-seal; крах там оставляет nonce незаписанным, но захваченный ciphertext нельзя переиграть — он привязан к nonce, который NEW уже поглотил. Действие оператора: никакого. Если `ERR_NONCE_REPLAY` когда-либо срабатывает на свежесгенерированном nonce — снять `recent_nonces.sealed` обеих нод и связаться с dev-perp.

## 10. СЛЕДУЮЩАЯ миграция — β17 → β18, одним пакетом (решено 2026-09-27)

**Пока не планируется по дате.** Второй пункт ниже — ещё замысел, ожидающий решения аудита,
поэтому у β18 нет ни MRENCLAVE, ни размера меты. Раздел существует затем, чтобы состав пакета
был решён ДО церемонии, а не под её давлением.

### 10.1 Что входит в β18

| изменение | почему нужна миграция | состояние |
|---|---|---|
| полоса кодов причин SPV (`xrpl_spv_host_rc`) | любое изменение анклава меняет MRENCLAVE | влито, `ad90ce4` |
| блокировка состояния (рекурсивная, все 31 вызов, касающийся состояния) | то же | влито, `df323f5` |
| клеймо `state_version` на каждой части | изменение **формата запломбированных файлов**: загрузчик и файлы должны двигаться вместе | замысел подан, `REQ-section-version-stamp.md` |

### 10.2 Почему одна миграция, а не три

Миграция — самый дорогой и рискованный шаг, и за одну неудачную попытку мы уже заплатили:
тогда холостой прогон **ни разу не загрузил** новый анклав на перенесённом состоянии и
пропустил церемонию, которую анклавы затем отвергли. Три подъёма — это три таких риска без
выигрыша: по отдельности ни одно из трёх изменений никого не держит, а третье как раз и
отпирает всё остальное.

### 10.3 Что отпирает β18

- **Возвращаются аттестованные часы.** Они намеренно погашены до тех пор, пока клеймо не
  **развёрнуто** (не «влито» — развёрнуто). `orchestrator/scripts/enable-attested-clock.sh`
  по умолчанию отказывается включать и объясняет причину; `--arm-anyway` — осознанный обход.
- **Можно переключать доверенный путь цены (вариант Б).** Проверка срока действия
  сертификата требует доверенного времени: с устаревшими часами сертификат не проверить, и
  путь цены останавливался бы на каждом опросе. Поэтому W5 и живое переключение стоят за
  часами, а часы — за β18.

Одна миграция лежит на критическом пути двух треков. Это причина сделать её правильно, а не
сделать её скорее.

### 10.4 Что этот пакет добавляет в предполётную проверку

- `orchestrator/src/path_a_capacity.rs` нужен размер меты β18, а
  `orchestrator/scripts/check-meta-sizes-vs-enclave.sh` должен проходить с заданным
  `ENCLAVE_REPO`. Это зеркало один раз уже отставало от анклава на две схемы и проявилось
  как ложный СТОП под давлением живой миграции — запускать страж при **обоих** деревьях, а не
  только в CI оркестратора, где он пропускается.
- `scripts/ci_perp_state_lock.py` и `scripts/ci_no_reason_on_the_wire.py` (репозиторий
  анклава) работают в `enclave-build`; `orchestrator/scripts/ci_prefix_framing.py` требует
  `ENCLAVE_REPO` для межрепозиторной половины.
- **ЭТА СТРОКА УТВЕРЖДАЛА ТО, ЧЕГО РЕАЛИЗАЦИЯ НЕ ДЕЛАЛА — до 2026-10-05.** Выяснилось
  запуском, а не чтением. Сухой прогон делал экспорт → импорт → самопроверку долговечности
  M3, которая распломбировывает ВНУТРИ уже работающего процесса NEW, после чего
  `reset_new_side_after_dry_run` удалял перенесённый набор и перезапускал NEW на ПУСТОМ
  каталоге. То есть единственный перезапуск во всей репетиции загружался ни на чём, а рунбук
  говорил, что репетиция покрывает шаг 5a. Для β18 это и был весь риск: проверяемое изменение
  — это проверка НА СТАРТОВОЙ ЗАГРУЗКЕ, значит единственное, что могло отказаться
  загружаться, было единственным, чего репетиция не касалась. Теперь сухой прогон выполняет
  загрузку ДО уборки, выносит по ней вердикт (набор на месте и не изменился, вернулся,
  сообщил о проверке миграционного манифеста, не напечатал отказа) и возвращает `boot_proof` в
  ответе. Сухой прогон — PASS только если 5a прошёл: `dry-run-ok` теперь значит и то и другое,
  а `dry-run-boot-failed` / `dry-run-boot-not-run` — отдельные статусы, потому что невыполненная
  проверка и пройденная проверка не должны делить одну строку.

- Шаг 5a из §3 — **загрузить** новый анклав на перенесённом состоянии во время холостого
  прогона. Именно отсутствие этого шага стоило нам подъёма; с клеймом он становится ещё
  важнее, потому что несовпадение клейма — это отказ загрузиться по замыслу.

### 10.5 ПРЕДПОЛЁТНОЕ условие, а не пожелание: корпус обновления на двух бинарях

Корпус проверок β18 работает в SIM-контейнере и покрывает всё, что можно покрыть **одной**
сборкой: порванный набор отклоняется, подправленное клеймо отклоняется иначе, отсутствующая
необязательная часть загружается, разрыв внутри части отклоняется. Он не может покрыть то, что
эта миграция и делает — загрузку набора β17 в анклав β18, — потому что **незаклеймённую** часть
умеет произвести только бинарь β17, а подделать её нельзя: клеймо лежит в подписываемом поле.

Логика ложного отказа посреди обновления покрыта исчерпывающе на хосте, против того же
накопителя, который исполняет анклав, — то есть рассуждение проверено. Не проверено сквозным
прогоном именно то, что делает церемония.

**Поэтому, прежде чем β18 будет ПОСТАВЛЕНА В ПЛАН, собрать оба бинаря и провести обновление
по-настоящему:**

1. собрать β17 (коммит до клеймения) и β18 из исходников в одной задаче;
2. прогнать сервер β17 через настоящий путь сохранения и получить подлинный набор β17;
3. загрузить этот набор в β18 — убедиться, что он **загружается**, распознаётся как старая
   схема и все части пересохраняются с клеймом;
4. загрузить второй раз — убедиться в чистой загрузке с уже **включённой** сверкой частей;
5. прервать обновление β18 посреди переименования кусков и загрузить снова — убедиться, что
   узел **поднимается** и доделывает обновление. Это тот случай, который в разборе положил бы
   узел, и которого одна сборка произвести не может;
6. убедиться, что блоб β17 читается байт в байт через исправленное чтение по фактическому
   размеру файла — этот путь чтения изменился для **всех** частей, не только для заклеймённых.

Пункт 5 и есть причина, по которой это условие, а не тест: он охраняет от узла, который не
поднимается после штатного обновления, и обнаруживается это посреди церемонии.


**У шага 1 есть две неочевидные предпосылки, обе выяснились при запуске (28.09.2026):**

- **Ключ подписи надо положить во вторую выкладку.** `Enclave/Enclave_private.pem` — локальный
  файл в gitignore, поэтому свежий `git worktree` или клон старого коммита его не содержит, и
  сборка падает с *«Failed to open file Enclave/Enclave_private.pem — Error happened while signing
  the enclave»*: это отказ **подписи**, а не компиляции, и читается как проблема в коде, которой
  нет. Использовать **один и тот же** ключ для обеих сборок правильно: он фиксирует MRSIGNER, а
  MRENCLAVE различается кодом — именно так выглядит один оператор, подписывающий два выпуска.
- **Каждый бинарник должен работать со своим хостом.** Два `perp-dex-server` между этими коммитами
  **не** идентичны, поэтому оснастка, собирающая два анклава и переиспользующая один хост,
  проверяет сочетание, которое никогда не поедет в производство.

Проверено на первом запуске шлюза: меры действительно различаются (β17 `1e5529eb…`, β18
`0183b242…`) при одном MRSIGNER — это и делает шаги 3–6 осмысленными, и это же объясняет, **почему**
их нельзя выполнить прямой загрузкой файлов β17.

**Почему шагам 3–6 нужна ЦЕРЕМОНИЯ, а не копирование файлов.** Каждая секция пломбируется с
`SGX_KEYPOLICY_MRENCLAVE`, поэтому β18 не может распечатать запломбированное β17 — «загрузить набор
в β18» невозможно как файловая операция. Работает это потому, что импорт Path-A **перепломбировывает**
выгруженный открытый текст под ключом β18, и по той же причине импортированный набор приходит без
штампов секций. Следствие вынесено на решение аудита, а не принято на веру. Значит корпус обязан
провести настоящие выгрузку и загрузку, а для них нужен кворум делегации против запломбированного
SignerList: обходного пути без подделанной подписи нет, а подделанная проверяла бы оснастку вместо
системы.


### 10.5.1 СЛИТО ≠ ПРОВЕРЕНО МИГРАЦИЕЙ — прочитать, прежде чем ссылаться на исправление как на доказательство

Исправление со штамповкой при импорте, для прогона которого этот шлюз и существует, **слито в
`main` репозитория анклава** (PR #172). Это сознательно **не** является доказательством, что оно
работает, и ради этого различия подраздел и написан, а не оставлен на догадку.

**Что слияние установило:** анклав с ним собирается; 24 хостовых утверждения чистого
предсканирования проходят, и шесть живых мутаций краснеют под AddressSanitizer; аудит вынес решение
по замыслу и проверил код первой рукой. Всё это — доказательства о **коде**.

**Чего слияние НЕ установило:** что набор β17 переживает церемонию внутрь анклава β18. Ни одна
миграция в репозитории пока не выполнена. Изменённый код относится **только** к пути миграции —
`apply_section_reseal_and_check` вызывается по одной секции внутри ecall'а импорта, а
`path_a_m3_self_check` есть самопроверка миграции, — поэтому на работающем кластере он лежит
**спящим** и слияние не изменило ни одного живого поведения. Спящий не значит проверенный.

**Поэтому наличие исправления в `main` этот шлюз не удовлетворяет, и никакое количество зелёного CI
тоже.** Шлюз удовлетворяется тем, что шесть шагов выше **прогнаны**, и в частности тем, что шаг 5
утверждает **отказ после исправления**: подставленный чанк с `save_seq = 0` в наборе с
`save_seq = 1` под проштампованной метой должен быть отвергнут. Это единственное утверждение и
показывает, что проверка при загрузке после миграции вооружена, — ради него исправление и писалось.

Записано потому, что дефект, который исправление устраняет, был **комментарием, которому поверил
будущий читатель**: он выводил следствие, верное в одном случае и неверное в другом. Слитый коммит
приглашает к той же самой ошибке в том же самом направлении, поэтому утверждение изложено здесь
словами, а не оставлено на вывод читателя.


### 10.5.2 Шлюз ПРОГНАН — что он засвидетельствовал и как его повторить

**Прогон 28.09.2026 на сборочном узле, закрыт аудитом по существу.** Между двумя SIM-серверами
проведена настоящая церемония Path-A β17→β18: генезис, внесение меры β18 в список допуска β17,
выгрузка, загрузка — и затем шесть шагов утверждений против импортированного набора.

    EthSignerEnclave/scripts/two-binary-upgrade-corpus.sh <b17-dir> <b18-dir> [old-port] [new-port]
    # ORCH_BIN=<бинарник оркестратора>, KEEP_DIR=1 чтобы сохранить рабочий каталог

Каждому каталогу нужны **свои** `enclave.signed.so` **и** `perp-dex-server`: два хостовых
бинарника между коммитами не идентичны, поэтому общий хост проверяет сочетание, которое никогда
не поедет в производство.

**Что засвидетельствовано.** β18 загружает набор, произведённый β17; схема обновляется
(перепломбированная мета растёт ровно на 8 байт — запись β17 в 184 байта становится записью β18 в
192); набор перепломбировывается со штампом и перечитывается начисто; **разрыв на загрузке после
миграции отвергается** кодом `-33`; **прерванный импорт падает закрыто** на распечатывании (`-30`);
и две разные формы пломбы обе читаются обратно.

**Что он различает** — свойство, которое шлюзу необходимо и которого проще всего не иметь. На
**до-исправленной** сборке β18 три утверждения краснеют: мета импорта приходит без штампа, рост
меты составляет +24 вместо +8, а разрыв на загрузке после миграции **ЗАГРУЖАЕТСЯ** вместо отказа.
Шаг 5 перенацелен именно потому, что первая его форма проходила на обеих сборках и, значит, не
свидетельствовала ни о чём — это выяснилось прогоном старого бинарника, а не чтением скрипта.

**Чего он не устанавливает и на что ссылаться нельзя:** воспроизводимость сборок (обе собрала одна
машина, а доказательство воспроизводимости подписали два аккаунта одного анклава — этот бандл
утверждает ложь и сдерживается лишь тем, что его ключи принадлежат одноразовым аккаунтам, которых
нет ни в одном производственном SignerList), кворум t-из-n, независимость операторов в любом виде.

**Шлюз открывает миграцию, но не назначает её.** Развёртывать ли β18 и когда — отдельное решение
со своими последствиями.

## 11. β18 ПОДГОТОВЛЕНА и ОСТАНОВЛЕНА на шлюзе воспроизводимости (28.09.2026)

Предполётная проверка завершена, миграция **не** начата. На живом кластере ничего не менялось —
все команды проверки были чтением.

### 11.1 Где остановились и почему это жёсткий стоп

`trusted_mrenclave_is_admitted` доверяет **себе всегда**, в остальном требует управляемого списка
допуска; при отсутствии такового «поведение до управления — строгое совпадение с собой, отказ по
умолчанию». Живой список **пуст на всех трёх узлах** (записей 0, эпоха 0), значит мера β18 не
допущена и выгрузка откажет с `PATH_A_ERR_MRENCLAVE_NOT_ADMITTED` (-25).

Для внесения нужны `TRUSTED_MRENCLAVES_REPRO_MIN = 2` **различных воспроизводителя**, подписывающих
хеш доказательства. Операторские аккаунты живых узлов входят в SignerList, и оркестраторы соберут
такой кворум сами — то есть **механически** это доступно.

**Именно поэтому это стоп, а не шаг.** Меру собрала одна машина. Сбор этих подписей заставил бы
**настоящие производственные операторские ключи** подписать утверждение «два различных
воспроизводителя подтвердили эту меру», которое **ложно**, — и, в отличие от тестового бандла, оно
было бы **годно везде**: любой производственный анклав примет по нему меру с `repro_count = 2`. Это
ровно тот обход воспроизводимости, который `REPRO_MIN` и существует предотвращать, изготовленный
одним сборщиком. Подпись сдерживается своим КЛЮЧОМ, а здесь ключи настоящие.

### 11.3 Порядок возобновления — **06.10.2026** (удержание владельца, продлено 01.10.2026)

> **Препятствие СМЕНИЛОСЬ, и различие существенно.** Квота GitHub Actions сбросилась 01.10.2026,
> как и ожидалось, конвейер GHA доступен — техническая преграда исчезла. Удержание с 01.10 по
> 06.10 есть **решение владельца о сроках**, а не ограничение. 1 октября ничего не делалось;
> читатель, нашедший это позже, не должен заключать, что шаги первого числа выполнены, и не должен
> искать их результаты.

1. **Собрать β18 конвейером GHA** с того же git-ref.
2. **Сверить её MRENCLAVE с `367cabb2…`** — сохранённым первым воспроизведением.
   - **Совпала** → два воспроизведения действительно состоялись, подписи операторов утверждают
     ПРАВДУ, бандл честен. Продолжаем.
   - **Не совпала** → сборка **не воспроизводима**, и это самостоятельная находка и стоп более
     жёсткий, чем нынешний. Не продолжать, разбираться с расхождением.
3. Внести меру в списки допуска всех трёх узлов (2 из 3 через реле оркестраторов).
4. Читать в ответе И `status`, И `boot_proof`: единственный PASS — это `dry-run-ok`, и он
   теперь требует загрузки 5a. Раньше `"status":"dry-run-ok"` возвращался без того, чтобы
   загрузка на перенесённом состоянии вообще происходила.
4. §3.1 разворачивание бок о бок, затем **сухой прогон** со ступенью 5a — ЗАГРУЗИТЬ новый анклав
   на перенесённом состоянии, — и только при успехе сухого прогона §3.2 **параллельно** на трёх узлах.

**Не срезать шаг 2 послаблением правила допуска.** Это правило и делает основание воспроизводимых
сборок несущим, а не декларативным, и цена его соблюдения — одна сборка и сверка.

### 11.4 Шага со списком допуска может вовсе не требоваться — ПРОВЕРИТЬ ЭТО ПЕРВЫМ при возобновлении

**Улика, найденная уже после остановки, и она исправляет моё допущение.** В живом каталоге лежит
`migration_manifest.sealed` — манифест M4, который пишет **завершённый** импорт Path-A, — рядом с
14 отставными наборами, несущими маркеры вывода. Значит живое состояние **пришло настоящими
миграциями с переносом**. При этом `trusted_mrenclaves.sealed` **ОТСУТСТВУЕТ**: управляемый список
допуска на этом кластере не пломбовался никогда.

Два факта вместе означают, что прежние миграции **завершились при несуществующем списке**. Либо
шлюз допуска появился позже них, либо он не лежит на том пути, которым идёт выгрузка.

**Я утверждал обязательность шага, прочитав исходник текущего `main`, а не проверив РАБОТАЮЩИЙ
двоичный файл** (`aead7ecf…`, сборка более старая). Это было допущение в одежде находки — ровно то,
от чего это же руководство постоянно предостерегает читателя.

**При возобновлении — и порядок здесь вынужденный, а не предпочтительный.** Опытная проверка
происходит НА шаге выгрузки в сухом прогоне, а значит **разворачивание бок о бок идёт первым**:
церемонии нужны `target_info` нового анклава и его эфемерная пара ключей, чтобы вообще дойти до
выгрузки, то есть новый должен уже работать на 9089. Разворачивание — это недеструктивная
предпосылка (`OLD is NOT touched`, пишется только в `perp-next/`), а не шаг, который можно
отложить за измерение.

Прежняя формулировка здесь гласила «прежде всего остального», что читается как «до
разворачивания» и отправляет внимательного читателя по невыполнимому пути. Аудит так и прочёл;
порядок — **разворачивание → сухой прогон → чтение кода**.

Итак: выяснить опытом, требует ли старый двоичный файл списка при выгрузке — например, дать **сухому прогону** дойти до шага выгрузки и прочитать код
возврата. `-25` (`PATH_A_ERR_MRENCLAVE_NOT_ADMITTED`) означает «требует»; успешная выгрузка —
«не требует».

**Если не требует, дилемма воспроизводимости исчезает целиком.** Запись в список не нужна, значит
подписывать «два различных воспроизводителя подтвердили меру» никому не придётся, и миграция идёт
на проверенной GHA сборке, не изготавливая вообще никакого удостоверения. Сверку 1 октября делать
всё равно стоит — она и делает сборку заслуживающей доверия, — но она перестанет быть тем, что
стоит между нами и церемонией.

**Если требует** — §11.3 остаётся как есть, и остановка была верна по обоим основаниям.

В любом случае этическое основание не меняется: *если* удостоверение допуска нужно, оно не должно
быть ложью, подписанной производственными ключами.

#### 11.4.1 Октябрьская сверка несущая в ОБЕИХ ветках

Заострено аудитом, и это самый чистый довод в её пользу, потому что он вообще не зависит от кода
возврата.

**Если выгрузка откажет с `-25`** — шлюз живой в работающем двоичном файле, удостоверение допуска
требуется, и воспроизведение через GHA есть то, что делает это удостоверение **правдой**, а не
ложью под производственными ключами.

**Если выгрузка пройдёт** — шлюз присутствует в исходнике и отсутствует в работающем файле, то
есть ни разу не исполнялся на кластере, который призван защищать, через четыре завершённые
миграции. Отсюда два следствия. Первое: **защита, существующая в коде и никогда не работавшая,
непроверена и в настоящий момент недейственна** — она читается как безопасность и ею не является.
Второе: **миграция самой β18 не защищена шлюзом** — выгрузка идёт в до-шлюзовом коде, значит анклав
вообще не проверяет ни допуск β18, ни её воспроизведение. Тогда за β18 ручаются только делегация
операторов 2-из-3 и воспроизведение через GHA, что делает сверку с `367cabb2…` **единственной
проверкой воспроизводимости, которую β18 получит.**

Шлюз начинает защищать лишь начиная с β18 — когда работать будет уже шлюзованный файл.

Итого: «требуется и должно быть правдой» либо «единственная проверка». Сверку делать в любом случае.

#### 11.3.1 Закрепить git-ref для сверки — `main` уже ушёл вперёд

Сохранённая мера `367cabb24ea4ae60b58075c4ec974b805077b0f6fac293b9e9954f8287baa308` собрана из
коммита анклава **`113cba2`**. К 01.10.2026 `main` анклава уже продвинулся дальше.

**Поэтому сборка через GHA должна целиться в `113cba2` явно, а не в `main`.** Сборка более позднего
ref даст другую меру **по законной причине** — другой код, — и это расхождение будет выглядеть в
точности как провал воспроизводимости, ничего при этом о воспроизводимости не доказывая. Сверка
имеет смысл только когда обе стороны собирают один и тот же исходник.

Если же β18 решено перезапустить с более нового ref, это сознательное решение: сохранённая мера
перестаёт применяться, первое воспроизведение обнуляется, и **нужны две свежие независимые сборки
нового ref**, прежде чем сверка снова что-то означает.
