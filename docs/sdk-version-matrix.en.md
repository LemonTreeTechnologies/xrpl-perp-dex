# SGX SDK version matrix — what runs where, what affects MRENCLAVE

**Status:** Accepted (2026-05-03).
**Audience:** maintainers, AI-Auditor, future external auditors, any new operator joining the cluster.
**Companions:** [`build-requirements.{en,ru}.md`](build-requirements.en.md) (Build / Sign / Run policy), [`multi-operator-architecture.{en,ru}.md`](multi-operator-architecture.en.md) (foundation invariants).

This document fixes the SGX SDK version state across our system. It exists because operator memory had been treating "the SDK" as a single version when in fact we have **three distinct SDK installations** that do not all agree, and the MRENCLAVE we ship is determined by which SDK was used at **build time** — not at runtime, not the operator's expectation. Confusing the layers led to a documented error in our reproducibility cross-check claims (initially mainnet was reported as MRENCLAVE `4dfe8997…`, which is actually the testnet/dev value; mainnet's MRENCLAVE is `cf65d92a…`, built with a different SDK before `Dockerfile.azure` even existed).

## 1. The three SGX layers and what each SDK affects

| Layer | Where the code lives | SDK at this layer determines | Linked at |
|---|---|---|---|
| **Trusted (in-enclave) code** | inside `enclave.signed.so` | the enclave's instruction bytes → MRENCLAVE | static-linked at **build time** from `libsgx_trts.a`, `libsgx_tcrypto.a`, `libsgx_tservice.a`, `libsgx_tprotected_fs.a`, `libsgx_dcap_tvl.a`, `libsgx_tstdc.a`, `libsgx_tcxx.a` |
| **Untrusted host bridge** | `Enclave_u.c` generated by `sgx_edger8r --untrusted` | host-side ECall marshalling code | compiled into `libapp.a`, then `perp-dex-server` binary, at **build time** |
| **Untrusted host runtime** | dynamic `libsgx_urts.so`, `libsgx_enclave_common.so`, etc. | enclave loading mechanics, AESM communication, syscall bridge | resolved at **runtime** via `LD_LIBRARY_PATH` / `/usr/lib/x86_64-linux-gnu/` |
| **DCAP attestation runtime** | dynamic `libsgx_dcap_quoteverify.so`, `libsgx_dcap_default_qpl.so` | quote generation + verification | resolved at **runtime** |
| **Platform services (AESM)** | systemd `sgx-aesm-service` | quote provisioning, PCK certificates, launch tokens | OS service at **runtime** |

The single most important fact: **MRENCLAVE is determined entirely by build-time inputs** — source code, EDL, `Enclave.config.xml`, **and the trusted-side libraries linked in (i.e., the build-time SDK).** Runtime SDK has zero effect on MRENCLAVE. Two operators can have completely different runtime SDK versions and run the same MRENCLAVE.

## 2. SDK version vs MRENCLAVE — the rule

> **Build with SDK 2.25 trusted libs → one MRENCLAVE. Build the same source with SDK 2.28 trusted libs → different MRENCLAVE.**

Empirical evidence on our system:

| What | Source code state | Build-time SDK trusted libs | Resulting MRENCLAVE |
|---|---|---|---|
| Mainnet `/opt/perp-dex/v0.1.0/enclave.signed.so` (April 7) | older code, pre-Dockerfile-azure | Hetzner local SDK ~2.25 (via `make` directly) | `cf65d92a60cc059052cc867b8150ed186a13a73dd34a8515fc8b36e611994eab` |
| Dev/testnet `/opt/perp-dex/v0.1.1/enclave.signed.so` + Azure cluster | commit `2c3d31f` | Dockerfile.azure SDK 2.28.100.1 | `4dfe899771bdb3f3097714013d054c08c7dd6e28f2acd17948f8a08f328c011b` |
| Build-gate clean rebuild from same testnet source | `infra/build-gate-fix-openssl` (post-fix) | Dockerfile.azure SDK 2.28.100.1 | `4dfe899771bdb3f3097714013d054c08c7dd6e28f2acd17948f8a08f328c011b` (bit-identical) |

`cf65d92a…` ≠ `4dfe8997…` and they cannot be made equal without changing inputs (either SDK back to 2.25, or accepting a MRENCLAVE bump).

## 3. Runtime compatibility — what loads where

| Build-time SDK (in enclave) | Runtime SDK (on host) | Loads? | Notes |
|---|---|---|---|
| 2.28 | 2.28 (Azure DCsv3) | ✅ yes | matched, expected case |
| 2.28 | 2.25/2.28 mixed (Hetzner) | ✅ yes — empirically | Intel maintains backwards-compat for `enclave_css.metadata.version=0x100000005` across SDK 2.x patch releases. Loading mechanics are architectural (defined by SGX hardware), libsgx_urts is just a marshaller. We see this work in production on Hetzner port 9089. |
| 2.25 | 2.25 (older Hetzner state) | ✅ yes — empirically | Mainnet on port 9088. |
| 2.25 | 2.28 (Azure) | ✅ presumed yes | Backwards-compat in this direction is even more reliable than the other. Not currently deployed in our cluster, untested by us. |
| Major SDK version mismatch (e.g., 1.x vs 2.x metadata) | — | ❌ no | Rare; would require Intel SGX SDK major bump. Not relevant to our 2.x line. |

**Implication:** the same `enclave.signed.so` artefact built once with SDK 2.28 **does run** on both Hetzner SGX1 (libsgx-urts 2.25) and Azure DCsv3 (libsgx-urts 2.28). Cross-machine DKG attestation evidence on testnet (per `feedback_dkg_cross_machine_bug.md`) confirms peer-to-peer attestation also works across this version gap.

## 4. The "two SDK types" framing in our project — what it means and what it doesn't

The naming `Dockerfile.azure` and the comment "matching Azure runtime" historically created the impression that we have an "Azure binary" and a "Hetzner binary." We don't, except by accident of when builds were done.

What is actually true:
- `Dockerfile.azure` was added 2026-04-08 to **make builds reproducible** — primary motivation was Azure DCsv3 cluster requiring all 3 peers to attest the same MRENCLAVE for FROST cross-machine signing. Pre-Dockerfile, builds were operator-laptop-or-Hetzner-local with whatever SDK happened to be installed → MRENCLAVE drift on every rebuild.
- `Dockerfile.azure` was named "azure" because that was the cluster motivating it. The output binary works equally on Hetzner SGX1 (without DCAP) for non-DCAP operations and on Azure DCsv3 (with DCAP) for full peer attestation.
- The MRENCLAVE differential between mainnet (`cf65d92a…`) and testnet (`4dfe8997…`) is **NOT** because one is "for Azure" and the other "for Hetzner." It's because they were built with **different SDK versions** at different points in time (April 7 with Hetzner local SDK ~2.25, vs subsequent builds via Dockerfile.azure with SDK 2.28).

## 5. Implications for foundation invariants 5 and 7

**Invariant 5 (upgrade-path-is-foundation, Path A):** when we Mode-S sync mainnet from `cf65d92a…` → some-Dockerfile.azure-built-MRENCLAVE, this is a **MRENCLAVE bump** (the SDK changed from 2.25-built to 2.28-built, so MRENCLAVE differs even if source code were unchanged). Path A migration ceremony is required for that sync to preserve customer state. There is no way to "stay at SDK 2.25 to keep cf65d92a stable" long-term — Intel's repo will eventually drop 2.25 packages.

**Invariant 7 (reproducibility N-of-M):** is the build-time SDK of all operators required to match? **Yes** — if even one operator's builder uses a different SDK version, their MRENCLAVE will differ from the others'. Reproducibility requires every operator to build via committed `Dockerfile.azure`, which pins SDK 2.28.100.1 and DCAP 1.25.100.1 across every libsgx-* package. Any divergence anywhere in those pins → MRENCLAVE divergence.

When the project upgrades the SDK (e.g., 2.28 → 2.29), the procedure is **lockstep**:

1. Bump every libsgx-* version pin in `Dockerfile.azure` to the new release
2. Bump the SDK installer URL (`sgx_linux_x64_sdk_X.YZ.binarno.bin`)
3. Bump DCAP packages if Intel pairs them differently in the new release
4. Rebuild on at least 2 environments, verify bit-identical MRENCLAVE
5. Plan Path A migration ceremony for the impending MRENCLAVE bump
6. After Path A succeeds, all operators upgrade their host runtime SDK to match (one-time, mechanically straightforward)

## 6. Why mainnet's `cf65d92a…` is NOT in our reproducibility chain

Stated explicitly so the audit trail is unambiguous:

- Mainnet's `enclave.signed.so` was built **2026-04-07**, a day before `Dockerfile.azure` was committed (`53e9b02`, 2026-04-08).
- At build time, the operator (Andrey on Hetzner) ran `make` directly with the locally-installed Intel SGX SDK at `/opt/intel/sgxsdk/`. That SDK is from May 2025 and contains `sgx_uae_epid.h` (a header Intel removed starting SDK 2.28), so it is approximately SDK 2.25-era.
- This binary's MRENCLAVE = `cf65d92a60cc059052cc867b8150ed186a13a73dd34a8515fc8b36e611994eab`.
- We have NOT reproduced this MRENCLAVE in any other environment because:
  - The build was outside Docker, so the toolchain depends on whatever was on the operator's host on April 7
  - SDK 2.25-era trusted libs are no longer installed on the Hetzner host (they were partially upgraded to 2.28 via apt during package updates)
  - We cannot rerun this build cleanly with the current Hetzner state

**Practical consequence:** mainnet's MRENCLAVE is an "operator-trust-only" measurement. Until we replace it via a fresh Dockerfile.azure-based deploy + Path A migration, the multi-operator security model has a gap: no auditor can verify "the deployed MRENCLAVE matches the source code" for mainnet specifically. Testnet is fully covered (Dockerfile.azure-based, three-way reproduced).

This is acceptable in `product-sandbox-single-operator` mode because real customer funds are not at stake. It is **NOT acceptable** for `production`-mode unlock without remediation.

## 7. Verification commands (operator quick-reference)

Check Hetzner host runtime SDK:
```bash
dpkg -l 2>/dev/null | grep -E "^ii  (libsgx-urts|libsgx-enclave-common|libsgx-headers|libsgx-quote-ex|libsgx-dcap-quote-verify|sgx-aesm-service|libsgx-pce-logic|libsgx-dcap-default-qpl) "
```

Check Azure DCsv3 host runtime SDK (via Hetzner bastion):
```bash
ssh azureuser@<azure-vm-ip> "dpkg -l 2>/dev/null | grep -E \"^ii  (libsgx-urts|libsgx-enclave-common|libsgx-headers|libsgx-quote-ex|libsgx-dcap-quote-verify|sgx-aesm-service|libsgx-pce-logic|libsgx-dcap-default-qpl) \""
```

Check the local build SDK on Hetzner (presence of EPID header indicates pre-2.28 SDK):
```bash
ls /opt/intel/sgxsdk/include/sgx_uae_epid.h 2>&1
```

Read MRENCLAVE from a built artefact:
```bash
source /opt/intel/sgxsdk/environment
sgx_sign dump -enclave enclave.signed.so -dumpfile /tmp/dump.txt -cssfile /tmp/css.bin
grep -A 2 "metadata->enclave_css.body.enclave_hash" /tmp/dump.txt | tail -2 | tr -d ' \n' | sed 's/0x//g'
```

Verify a clean Docker rebuild matches another operator's MRENCLAVE:
```bash
cd EthSignerEnclave
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -pkeyopt rsa_keygen_pubexp:3 -out Enclave/Enclave_private.pem
docker build --no-cache -f Dockerfile.azure -t enclave-cross .
CID=$(docker create enclave-cross)
docker cp "${CID}:/build/out/enclave.signed.so" /tmp/
docker rm "${CID}"
docker run --rm -v /tmp:/out enclave-cross bash -c 'source /opt/intel/sgxsdk/environment && sgx_sign dump -enclave /out/enclave.signed.so -dumpfile /out/dump.txt'
grep -A 2 "metadata->enclave_css.body.enclave_hash" /tmp/dump.txt | tail -2 | tr -d ' \n' | sed 's/0x//g'
```
