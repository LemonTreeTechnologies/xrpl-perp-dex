# SGX SDK version matrix — что где работает, что влияет на MRENCLAVE

**Status:** Принято (2026-05-03).
**Audience:** maintainer'ы, AI-Auditor, future external auditor'ы, любой новый оператор присоединяющийся к кластеру.
**Companions:** [`build-requirements.{en,ru}.md`](build-requirements.ru.md) (Build / Sign / Run policy), [`multi-operator-architecture.{en,ru}.md`](multi-operator-architecture.ru.md) (foundation invariants).

Этот документ фиксирует SGX SDK version state across нашу систему. Существует потому что operator memory considered "the SDK" как single version, в то время как у нас на самом деле **три distinct SDK installations** которые не все agree, и MRENCLAVE который мы ship определяется тем какой SDK был использован на **build time** — не runtime, не operator's expectation. Confusing the layers привело к documented error в нашем reproducibility cross-check claim'е (initially mainnet был reported как MRENCLAVE `4dfe8997…`, что на самом деле testnet/dev value; mainnet's MRENCLAVE — это `cf65d92a…`, built с разным SDK до того как `Dockerfile.azure` вообще существовал).

## 1. Три SGX layers и что каждый SDK affects

| Layer | Где код живёт | SDK на этом слое определяет | Linked at |
|---|---|---|---|
| **Trusted (in-enclave) code** | внутри `enclave.signed.so` | bytes enclave instructions → MRENCLAVE | static-linked at **build time** из `libsgx_trts.a`, `libsgx_tcrypto.a`, `libsgx_tservice.a`, `libsgx_tprotected_fs.a`, `libsgx_dcap_tvl.a`, `libsgx_tstdc.a`, `libsgx_tcxx.a` |
| **Untrusted host bridge** | `Enclave_u.c` generated by `sgx_edger8r --untrusted` | host-side ECall marshalling code | compiled в `libapp.a`, потом `perp-dex-server` binary, на **build time** |
| **Untrusted host runtime** | dynamic `libsgx_urts.so`, `libsgx_enclave_common.so`, etc. | enclave loading mechanics, AESM communication, syscall bridge | resolved на **runtime** через `LD_LIBRARY_PATH` / `/usr/lib/x86_64-linux-gnu/` |
| **DCAP attestation runtime** | dynamic `libsgx_dcap_quoteverify.so`, `libsgx_dcap_default_qpl.so` | quote generation + verification | resolved на **runtime** |
| **Platform services (AESM)** | systemd `sgx-aesm-service` | quote provisioning, PCK certificates, launch tokens | OS service на **runtime** |

Самый важный fact: **MRENCLAVE определяется entirely build-time inputs** — source code, EDL, `Enclave.config.xml`, **и trusted-side libraries linked in (т.е. build-time SDK).** Runtime SDK имеет zero effect на MRENCLAVE. Два operator'а могут иметь completely different runtime SDK versions и run тот же MRENCLAVE.

## 2. SDK version vs MRENCLAVE — правило

> **Build с SDK 2.25 trusted libs → один MRENCLAVE. Build тот же source с SDK 2.28 trusted libs → разный MRENCLAVE.**

Empirical evidence на нашей системе:

| Что | Source code state | Build-time SDK trusted libs | Resulting MRENCLAVE |
|---|---|---|---|
| Mainnet `/opt/perp-dex/v0.1.0/enclave.signed.so` (April 7) | older code, pre-Dockerfile-azure | Hetzner local SDK ~2.25 (через `make` напрямую) | `cf65d92a60cc059052cc867b8150ed186a13a73dd34a8515fc8b36e611994eab` |
| Dev/testnet `/opt/perp-dex/v0.1.1/enclave.signed.so` + Azure cluster | commit `2c3d31f` | Dockerfile.azure SDK 2.28.100.1 | `4dfe899771bdb3f3097714013d054c08c7dd6e28f2acd17948f8a08f328c011b` |
| Build-gate clean rebuild от того же testnet source | `infra/build-gate-fix-openssl` (post-fix) | Dockerfile.azure SDK 2.28.100.1 | `4dfe899771bdb3f3097714013d054c08c7dd6e28f2acd17948f8a08f328c011b` (bit-identical) |

`cf65d92a…` ≠ `4dfe8997…` и они не могут быть made equal без changing inputs (либо SDK обратно в 2.25, либо accepting MRENCLAVE bump).

## 3. Runtime compatibility — что грузится где

| Build-time SDK (in enclave) | Runtime SDK (на host) | Loads? | Notes |
|---|---|---|---|
| 2.28 | 2.28 (Azure DCsv3) | ✅ да | matched, expected case |
| 2.28 | 2.25/2.28 mixed (Hetzner) | ✅ да — empirically | Intel maintains backwards-compat для `enclave_css.metadata.version=0x100000005` across SDK 2.x patch releases. Loading mechanics architectural (defined SGX hardware), libsgx_urts только marshaller. Это работает в production на Hetzner port 9089. |
| 2.25 | 2.25 (older Hetzner state) | ✅ да — empirically | Mainnet на port 9088. |
| 2.25 | 2.28 (Azure) | ✅ presumed yes | Backwards-compat в этом direction даже более reliable чем другой. Currently не deployed в нашем кластере, untested by us. |
| Major SDK version mismatch (e.g., 1.x vs 2.x metadata) | — | ❌ нет | Rare; would require Intel SGX SDK major bump. Не relevant к нашей 2.x line. |

**Implication:** тот же `enclave.signed.so` artefact built once с SDK 2.28 **does run** на обоих Hetzner SGX1 (libsgx-urts 2.25) И Azure DCsv3 (libsgx-urts 2.28). Cross-machine DKG attestation evidence на testnet (per `feedback_dkg_cross_machine_bug.md`) подтверждает что peer-to-peer attestation также работает across этого version gap.

## 4. Framing "two SDK types" в нашем проекте — что значит и что не значит

Naming `Dockerfile.azure` и комментарий "matching Azure runtime" исторически создали впечатление что у нас "Azure binary" и "Hetzner binary." Не имеем, кроме как accident от того когда builds были done.

Что actually true:
- `Dockerfile.azure` был добавлен 2026-04-08 чтобы **make builds reproducible** — primary motivation был Azure DCsv3 cluster requiring all 3 peers attest the same MRENCLAVE для FROST cross-machine signing. Pre-Dockerfile, builds были operator-laptop-or-Hetzner-local с whatever SDK happened to be installed → MRENCLAVE drift на каждом rebuild.
- `Dockerfile.azure` named "azure" потому что это был cluster motivating it. Output binary works equally на Hetzner SGX1 (без DCAP) для non-DCAP operations и на Azure DCsv3 (с DCAP) для full peer attestation.
- MRENCLAVE differential между mainnet (`cf65d92a…`) и testnet (`4dfe8997…`) **NOT** потому что один "for Azure" а другой "for Hetzner." Это потому что они были built с **разными SDK versions** в разных моментах времени (April 7 с Hetzner local SDK ~2.25, vs subsequent builds через Dockerfile.azure с SDK 2.28).

## 5. Implications для foundation invariants 5 и 7

**Invariant 5 (upgrade-path-is-foundation, Path A):** когда мы Mode-S sync'ним mainnet от `cf65d92a…` → some-Dockerfile.azure-built-MRENCLAVE, это **MRENCLAVE bump** (SDK changed from 2.25-built to 2.28-built, поэтому MRENCLAVE differs даже если source code unchanged). Path A migration ceremony required чтобы тот sync preserve customer state. Нет способа "stay at SDK 2.25 to keep cf65d92a stable" long-term — Intel's repo eventually drop 2.25 packages.

**Invariant 7 (reproducibility N-of-M):** обязан ли build-time SDK всех operators match? **Да** — если хоть один operator's builder uses разный SDK version, их MRENCLAVE differs от others'. Reproducibility requires every operator build через committed `Dockerfile.azure`, который pins SDK 2.28.100.1 и DCAP 1.25.100.1 across every libsgx-* package. Любой divergence anywhere в тех pins → MRENCLAVE divergence.

Когда проект upgrade'ит SDK (e.g., 2.28 → 2.29), procedure — **lockstep**:

1. Bump every libsgx-* version pin в `Dockerfile.azure` к новому release
2. Bump SDK installer URL (`sgx_linux_x64_sdk_X.YZ.binarno.bin`)
3. Bump DCAP packages если Intel pairs их differently в новом release
4. Rebuild на ≥2 environments, verify bit-identical MRENCLAVE
5. Plan Path A migration ceremony для impending MRENCLAVE bump
6. После Path A succeeds, все operators upgrade свой host runtime SDK to match (one-time, mechanically straightforward)

## 6. Почему mainnet's `cf65d92a…` НЕ в нашей reproducibility chain

Stated explicitly чтобы audit trail был unambiguous:

- Mainnet's `enclave.signed.so` был built **2026-04-07**, на день раньше `Dockerfile.azure` был committed (`53e9b02`, 2026-04-08).
- На build time, operator (Andrey на Hetzner) запустил `make` напрямую с locally-installed Intel SGX SDK на `/opt/intel/sgxsdk/`. Тот SDK от May 2025 и содержит `sgx_uae_epid.h` (header который Intel removed starting SDK 2.28), так что approximately SDK 2.25-era.
- MRENCLAVE этого binary = `cf65d92a60cc059052cc867b8150ed186a13a73dd34a8515fc8b36e611994eab`.
- Мы NOT reproduced этот MRENCLAVE в любом другом environment потому что:
  - Build был outside Docker, поэтому toolchain depends на whatever был на operator's host на April 7
  - SDK 2.25-era trusted libs no longer installed на Hetzner host (они partially upgraded к 2.28 через apt during package updates)
  - Не можем rerun этот build cleanly с current Hetzner state

**Practical consequence:** mainnet's MRENCLAVE — это "operator-trust-only" measurement. Пока мы не replace это через fresh Dockerfile.azure-based deploy + Path A migration, multi-operator security model has gap: no auditor может verify "deployed MRENCLAVE matches source code" для mainnet specifically. Testnet fully covered (Dockerfile.azure-based, three-way reproduced).

Это acceptable в `product-sandbox-single-operator` mode потому что real customer funds не at stake. Это **NOT acceptable** для `production`-mode unlock без remediation.

## 7. Verification commands (operator quick-reference)

Check Hetzner host runtime SDK:
```bash
dpkg -l 2>/dev/null | grep -E "^ii  (libsgx-urts|libsgx-enclave-common|libsgx-headers|libsgx-quote-ex|libsgx-dcap-quote-verify|sgx-aesm-service|libsgx-pce-logic|libsgx-dcap-default-qpl) "
```

Check Azure DCsv3 host runtime SDK (через Hetzner bastion):
```bash
ssh azureuser@<azure-vm-ip> "dpkg -l 2>/dev/null | grep -E \"^ii  (libsgx-urts|libsgx-enclave-common|libsgx-headers|libsgx-quote-ex|libsgx-dcap-quote-verify|sgx-aesm-service|libsgx-pce-logic|libsgx-dcap-default-qpl) \""
```

Check local build SDK на Hetzner (presence EPID header indicates pre-2.28 SDK):
```bash
ls /opt/intel/sgxsdk/include/sgx_uae_epid.h 2>&1
```

Read MRENCLAVE из built artefact:
```bash
source /opt/intel/sgxsdk/environment
sgx_sign dump -enclave enclave.signed.so -dumpfile /tmp/dump.txt -cssfile /tmp/css.bin
grep -A 2 "metadata->enclave_css.body.enclave_hash" /tmp/dump.txt | tail -2 | tr -d ' \n' | sed 's/0x//g'
```

Verify clean Docker rebuild matches another operator's MRENCLAVE:
```bash
cd EthSignerEnclave
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -pkeyopt rsa_keygen_pubexp:3 -out Enclave/Enclave_private.pem
docker build --no-cache -f Dockerfile.azure -t enclave-cross .
CID=$(docker create enclave-cross)
docker cp "${CID}:/build/out/enclave.signed.so" /tmp/
docker rm "${CID}"
docker run --rm -v /tmp:/out enclave-cross bash -c 'source /opt/intel/sgxsdk/environment && sgx_sign dump -enclave /out/enclave.signed.so -dumpfile /out/dump.txt'
grep -A 2 "metadata->enclave_css.body.enclave_hash" /tmp/dump.txt | tail -2 | tr -d ' \n' | sed 's/0x//g'
```
